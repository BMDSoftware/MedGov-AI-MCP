# Worries / Scalability concerns

**Multi-user task queue saturation** - worth writing up in the paper (limitations/deployment section).

The task runner uses a shared `ThreadPoolExecutor`. Each inference or cellpose task holds a thread even while blocking on its semaphore waiting for its turn to run. With only 4 workers (now raised to `os.cpu_count() + 4`), multiple concurrent users can fill all thread slots with tasks that are just waiting, leaving new tasks stuck in the executor queue with no thread to run in.

Key points:
- The **semaphores** are what protect the server from OOM - only 1 inference and 1 cellpose run at a time regardless of how many users submit tasks. This is correct and safe.
- The **thread count** only controls how many tasks can be *waiting* simultaneously. More threads = more concurrent waiters, not more concurrent model runs.
- What would crash the server: removing the semaphores. 20 users each loading a 2GB model at once = 40GB RAM = OOM crash. The semaphores prevent this.
- The fix applied: `TASK_MAX_WORKERS` env var, defaults to `min(32, os.cpu_count() + 4)`. Can be set higher in `.env` on the deployment machine if needed.
- Added watched-dir count and task worker metrics to the Settings debug panel so this is now visible at runtime.

**TODO for paper**: mention this as a deployment consideration - single-machine shared thread pool means inference is always serialized (one at a time). For a production multi-tenant deployment, a proper task queue (Celery, RQ, or similar) with a dedicated worker process per GPU would be the right architecture. The current design is appropriate for a research prototype and small clinical deployments.
